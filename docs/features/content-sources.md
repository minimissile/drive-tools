# 公共内容采集与渠道复用

设计日期：2026-10-26。本文先于本轮重构建立。

## 问题与目标

皮皮虾是内容来源，不属于知乎业务。上一版把采集入口、图片存储、IPC 和同帖导入状态绑定知乎，其他渠道无法直接复用。此次将采集作为工作空间内的公共功能，保留原帖图文、评论和来源；由独立渠道适配器创建各渠道草稿。

## 工作流

1. 工作台“通用内容操作 → 皮皮虾采集”，提供唯一采集工作区。知乎和微博页面提供前往公共采集页的快捷入口，不保留两套采集界面。
2. 采集、预览、选择图片和评论继续沿用现有流程，输入暂存按工作空间和原帖隔离。采集不要求选择渠道或账号。
3. 用户选择“知乎素材池”或“微博草稿”；知乎进入待审核素材，微博明确选择账号后创建本地待编辑草稿，默认仅自己可见。支持同一原帖用于不同渠道。
4. 去重按“来源、原帖、渠道、目标账号”保存独立交付记录。知乎不依赖账号，微博草稿绑定账号。已交付的草稿不会因重新采集、切换渠道或重复点击而被覆盖。
5. 页面展示各去向记录及继续编辑入口；微博复用现有图文编辑器，不新增第二套上传或发布逻辑。交付失败保留选择并在操作旁说明原因。

## 架构

- `core/pipix/`：只负责皮皮虾公开页、来源持久化、图片采集、选择校验及交付编排，不导入知乎或微博服务。
- `shared/content-sources.ts`：渠道无关的图片引用、来源、素材包和交付记录。`shared/pipix.ts` 定义来源及 `pipix.*` IPC，不再扩展知乎契约。
- `core/content-assets.ts`：公共内容图片的保存、边界检查、哈希核验和路径解析；新采集图片保存到 `content-assets`。旧 `zhihu-assets` 仅作为已有记录兼容位置。
- `AppService`：独立组装公共采集服务，通过目的地接口注入知乎、微博本地草稿创建能力。渠道服务承担自身的字数、账号、状态和审核规则。
- `src/pipix/`：独立公共页面及领域组件，不依赖 `src/zhihu` 的状态或样式。继续使用公共 UI、IPC 查询和草稿暂存。
- 交付时先检查图片，再在同一数据库事务中创建渠道草稿与交付记录，避免出现重复或半成品草稿。所有交付仅为本地保存，不自动填写或发布。

## 兼容与验证

增量迁移保留旧采集数据；旧 `contentId` 转为知乎交付记录，已有图片继续可读，已有知乎草稿不改写。公共图片和各渠道引用一起纳入备份核验，恢复撤销既有审核与调度授权。原输入与选择暂存键沿用，不恢复发布确认。

本轮沿用用户最初明确授权的自动化测试范围，使用临时数据库、模拟采集与模拟平台端口，覆盖旧数据迁移、双渠道复用、账号隔离去重、字数限制、图片故障、备份恢复及桌面操作。复用现有源码服务，不新开桌面、不制作安装包、不真实发布。

已交付版本的采集范围是公开分享链接、正文配图和分享页文字评论。下述列表发现扩展另行描述；完整评论分页、视频或评论内图片下载不在本轮范围内。

## 列表发现扩展（2026-10-26，开发前设计）

目标：无需逐条寻找分享链接，先按关键词、作者、话题或推荐入口获得帖子列表，再勾选批量采集到同一个公共素材库，继续复用已有图片存储、评论选择及知乎／微博交付流程。

调研结论与来源：

- [皮皮虾官网](https://www.pipix.com/)当前是下载与创作入口，未发现公开推荐列表；既有官方分享页可以读取单帖，但不能因此推断存在可匿名使用的列表接口。
- [TikHub 公开 OpenAPI](https://api.tikhub.io/openapi.json)列出 `fetch_home_feed`、`fetch_search`、`fetch_user_post_list`、`fetch_hashtag_post_list`。搜索的 `search_type=3` 为图文，列表通过 `offset` 或 `loadmore_cursor` 翻页，作者／话题另传 `feed_count`。这是第三方服务，不是皮皮虾官方开放接口，须 Bearer API Key，请求可能计费。
- [TikHub 搜索说明](https://docs.tikhub.io/258871430e0)的响应示例仅给出通用封装，`data=null`，没有保证稳定的业务数据结构。实现必须拒绝不识别的结构，不能显示为“0 条”；真实响应结构和数据覆盖率需配置 Key 后联调确认。
- Apify 上的 [推荐流服务](https://apify.com/ethereal_wool/pipixia-feed-scraper)主要面向视频，与当前图文目标不完全匹配，本轮不接入。

实现约束：

1. 列表适配器独立于公开页客户端和发布渠道，默认图文关键词搜索，另提供推荐／作者／话题入口。只使用有文档的查询端点，不修改浏览量或互动数据。
2. API Key 经现有系统加密凭据服务保存；前端只读取配置状态，输入不暂存，不放入 URL、日志、普通设置或备份。
3. 每次明确点击只请求一页，不自动翻页、自动重试或后台付费轮询。显示第三方及计费提示；配置保存、页面打开和本地列表刷新均不请求远端。
4. 列表仅返回候选帖子，使用精确字符串 ID 生成官方详情地址；批量勾选最多 20 条并复用现有采集队列。图片与评论范围仍以分享页实际返回为准，不把推荐中的视频封面当作配图，也不把高赞自动标为神评。
5. 查询失败保留已有候选和选择，未知结构明确报错；分页游标不前进时停止翻页，列表去重，避免重复计费循环。切换查询条件后重新开始，不复用旧游标。
6. 初轮自动化验证只使用临时数据库、模拟接口及现有源码服务，不调用真实计费接口，不发布内容。用户随后保存 Key 并明确要求继续测试、实测上限，追加的真实查询范围与结果见下文“本地知识库与容量实测验收”；不把模拟通过视为所有真实端点均已验证。

## 已实现的使用方式

### 本地入库与统一配置扩展（2026-10-26，开发前补充）

- TikHub Key 改由“连接与设置 → 内容数据源”统一维护，复用已有密钥输入与加密保存流程；采集页仅展示状态及跳转。取消此前只允许字母、数字和少数标点的过严校验，兼容完整 Key、Bearer 前缀和首尾空白；仍拒绝请求头不允许的空格／换行。
- 单次获取量：当前四类端点均无 `count`／`page_size` 参数，`feed_count` 是翻页序号，不能当作数量。完整保存每次响应，不以界面 6 条分页、20 条采集选择或原 200 条解析上限裁掉返回数据。不承诺上游单次固定条数。
- 本地内容知识库与流量词知识库按职责分开；复用公共响应凭据清理方法、SQLite 迁移和备份机制。保存完整响应、规范查询参数、抓取时间、解析状态和去重帖子索引；图库与评论的原始数据随响应保留，显示筛选不影响入库。
- 同一查询、游标与页序号默认使用已存响应。页面打开、搜索本地、翻阅本地分页和重启恢复均不请求远端；显式请求新页才访问接口。“重新请求第一页”须清楚标明将访问服务商。解析失败也先保存响应，修复后可本地重解析，避免重复计费。
- 采集若已有列表中的完整图文信息则优先复用；缺少必要信息时仍沿用公开详情页。数据库中的知识条目供多渠道共用，不自动发布。凭据不进入响应归档或备份。

1. 打开“工作台 → 通用内容操作 → 皮皮虾采集”。知乎运营与微博图文营销顶部的“公共素材采集”也进入同一个页面。
2. “获取数据列表”中新用户默认进入本地知识库，已有工作空间保留上次来源选择。先在“连接与设置 → 内容数据源 → TikHub API Key”保存 Key；兼容完整 Key、`Bearer ` 或 `Authorization: Bearer ` 前缀及首尾空白，不显示回填、不随表单暂存。切换图文关键词搜索、首页推荐、作者作品或话题作品，输入条件后明确点击“获取列表”才访问服务商，可能计费；默认复用同条件、游标和页序号的归档。若需重新获取，使用标有远端请求含义的“重新请求第一页”。全部返回行先入库，界面的 6 条本地分页及最多 20 条采集选择不裁剪入库数据。勾选后“采集所选”优先复用完整的列表图文信息，必要时读取公开分享页。查询失败保留结果与选择，提供显式重试，不自动重试。真实图文搜索已验证，其他入口仍只有模拟验证。
   本地检索、分页、刷新和“重建本地索引”均不请求服务商。远端续页仅采用返回的游标；本轮真实搜索未返回游标，页面显示“暂无可续页进度”，不猜测偏移量。容量探测位于统一设置的“单次返回量实测”，重复相同探测复用本地响应。
3. “分享链接”仍支持每行粘贴一条链接或分享文案，最多 20 行；采集后选择图片、评论并填写素材标题。两种入口共用采集队列和本地来源记录，失败结果显示输入链接，可单项或批量重试。
4. 在“用于渠道草稿”选择去向。知乎不要求先选账号，点击“送入知乎素材池”后进入待审核状态；选择微博时必须指定已核验账号，正文与所选评论合计不得超过 2000 字符，超限不截断。
5. 微博点击“创建微博草稿”后只保存本地文本和配图，默认仅自己可见；“打开微博草稿”复用现有发布编辑器，可继续修改及“保存本地草稿”。指定草稿读取完成前禁止编辑；找不到时可重试。原有手写草稿使用独立暂存，不被此次打开操作覆盖。
6. “已使用的去向”展示各渠道、微博账号名称和 UID。切回其他渠道或移除账号后仍保留历史标识；重复创建返回原草稿，保留后来编辑的文本及配图。旧记录没有账号快照时用实际账号 ID 区分。
7. 后续填写、上传、发布继续通过对应渠道的既有明确操作进行。公共采集服务不启动知乎调度，也不代为提交微博。

## 数据与备份落实

- 采集接口独立为 `pipix.list / collect / image / export`；从知乎服务和契约中移除采集依赖。公共图片读写由 `core/content-assets.ts` 承担。
- 列表与知识库接口为 `pipix.discoveryConfig / saveDiscoveryKey / discover / knowledge / reindex / probeCapacity`。自动读取仅访问本地配置状态与知识库；列表和容量探测均是显式命令。统一设置沿用 `secret.save` 及系统加密服务。`core/pipix/discovery.ts` 负责远端请求与分页解析，`core/pipix/knowledge.ts` 负责响应归档、索引、缓存和本地续页进度；不直接依赖渠道。真实响应确认了嵌套的 `data.data.data` 列表结构，未知结构明确报错并保留原始响应，不以空态掩盖上游变化。
- 数据库从 v20 增量迁移到 v21，新增渠道交付表，再迁移到 v22 新增通用响应归档、去重知识条目和归档命中关系。旧 `contentId` 转成知乎交付记录；旧图片位置加兼容标记，已有知乎稿件与审核状态不因升级改变。迁移前保留备份。
- 响应先保存后解析，包括解析失败的响应；保留全部行、正文、图片 URL、评论与其他字段，不再使用旧 200 行解析上限和 500 字截断。单响应物理读取边界为 32 MiB。响应按查询、游标及代次归档，帖子按来源与精确字符串 ID 去重；已保存 HTTP 200 响应可以离线重建索引。列表高亮 `<em>` 只在展示字段移除，原始响应保持原样。
- 归档复用公共响应凭据清理方法，Key 不进入归档、普通设置或备份。v22 知识库纳入工作空间备份和恢复；恢复后保留响应与帖子，凭据和发布授权仍按原规则剥离。
- 新采集图片写入 `content-assets`，知乎和微博共享文件引用，不重复生成图片。微博来源草稿替换本地图片也进入公共存储，继续支持 PNG/JPG/GIF；皮皮虾动态原图仍按既有采集策略保存为静态 PNG。
- 备份核验公共图片、旧知乎图片及两个渠道的引用。恢复保留公共来源与交付记录，并对白名单内的微博来源草稿保留内容；编辑稿恢复为待检查，曾上传或提交的记录恢复为待核对，剥离环境信息，不恢复上传/发布授权。
- 本次保留项目已有的关键词和资料匹配类型与能力，没有另建选题体系。未来增加渠道时，在公共契约中声明目的地，并由应用服务注入对应本地草稿适配器；采集客户端、原帖解析和存储不需要导入渠道服务。

### 本地知识库与容量实测验收（2026-10-26）

用户在统一设置保存 Key 后，明确授权继续测试及在无定义时试出单次获取上限。检查 [TikHub OpenAPI](https://api.tikhub.io/openapi.json) 的四类列表端点，未发现可声明单次条数的 `count` 或 `page_size`；作者、话题的 `feed_count` 表示翻页次数。为验证未文档化参数，固定图文搜索 `keyword=生活趣事`、`search_type=3`、`offset=0`，进行了以下真实请求：

| 请求 | 附加参数 | HTTP | 实际返回 |
| --- | --- | --- | --- |
| 基准查询 | 无 | 200 | 10 条（7 图文、3 文字） |
| 容量探测 1 | `count=20` | 200 | 10 条 |
