## 0.0.2 → 0.0.3 差分下载专项

使用上述最终 ZIP 与 0.0.2 基线完成差分下载、校验和回退复测，五个隔离场景全部通过，结果保存于 `release-evidence/0.0.3/differential/result.json`。成功差分场景的观测如下：

| 项目 | 结果 |
| --- | --- |
| 0.0.3 完整 ZIP | 133,632,351 字节 |
| 差分 ZIP 载荷 | 9,005,308 字节 |
| 新旧 blockmap 合计 | 297,351 字节 |
| ZIP 载荷与 blockmap 合计 | 9,302,659 字节，约 8.87 MiB |
| Range 请求 | 44 次 |
| 全量 ZIP 请求 | 0 次 |
| ZIP 载荷节省比例 | 93.26%，不含 blockmap 与 HTTP 开销 |

五个场景分别为：

1. 有旧缓存时完成差分重建，最终 ZIP 通过 SHA512 校验。
2. 无旧缓存时回退全量下载并通过校验。
3. 旧 blockmap 返回 404 时回退全量下载并通过校验。
4. Range 内容损坏时拒绝差分重建结果，回退全量并通过校验。
5. 全量包损坏时由 SHA512 校验拒绝，未触发原生安装。

专项复用真实 macOS 更新器的下载、重建、校验与回退链，通过本机回环 HTTP 服务提供发行产物。差分传输量按 ZIP 载荷与 blockmap 统计，不含 HTTP 开销，不承诺每个版本或网络环境获得相同节省比例。该隔离专项本身没有执行真实 GitHub 公网下载、原生安装、重启或生产应用替换；后续生产操作结果单独记录如下。

## 启动故障与原因

新应用未显示主窗口。隔离工作树通过 `node_modules` 符号链接共享依赖，触发打包收集缺失，发行包遗漏 `fs-extra`、`debug` 等传递运行时依赖。应用在启动早期因依赖缺失触发异常，并被 NSAlert 阻塞。

此前通过的签名、公证、Gatekeeper、构建文件及源码映射核对没有覆盖完整运行时依赖闭包；下载哈希一致也只能证明下载内容与该故障发行包一致。此次结果不能记录为成功升级或正常启动。
